# 产物管理 v3 规划：从「分类」改成「角色 × 类型」

> 状态：**规划稿，未实现**。数据基线：2026-11-06，真实工作区 142 条。
> 前稿：`plugin-design-v2-category-autosync.md`（被本文取代，结论有修正）。

---

## 0. 先说三个核对出来的事实

### 事实 1：这 142 条里，真正的产物大约只有 22 条

| 角色 | 条数 | 都是些什么 |
|---|---|---|
| 过程（scratch） | 103 | 51 张截图 + 42 个 harness 脚本 + fixture |
| 记忆（memory） | 17 | `MEMORY.md` ×13 + `PERSONA.md` ×3 + `HANDOFF.md` |
| 交付物（deliverable） | 22 | 设计文档、计划、README、少量脚本 |
| **用户上传的素材** | **0** | 见事实 2 |

### 事实 2：工作区里没有「用户上传的文件」

DSH 把用户上传物存在 `~/.dsh/attachments/v1/`（377 个内容寻址 blob），**不进工作区**。
我按 sha256 把 142 个文件与 377 个 blob 全量比对，只命中 3 个（而且那 3 张是我生成、又被我自己读回过的截图）。

**结论：那 51 张截图不是「你上传的素材」，是我跑测试/验收时生成的过程证据。**
所以要解决的核心问题不是「上传 vs 生成」，而是：

> **过程性文件（截图/测试脚本/夹具）把交付物淹没了。**

这个区分更有价值，也更容易规则化——但它**不可能 100% 自动**（见 §4.3）。

### 事实 3：真正的交付物可能根本不在会话目录里

插件只扫 `<工作区>/sessions` 和 `<工作区>/artifacts`（`lib/indexer.js:66`）。
本次会话的交付物是 `D:\workspace\dsh\dsh-plugin-artifacts\` —— **在扫描范围之外**，插件看不见。
所以「备份产物」这件事，得先回答：**哪些目录算产物区？**

## 1. 现有分类为什么不够

| 问题 | 表现 |
|---|---|
| 类型回答的是「格式」 | 8 个 chip（网页/幻灯片/文档/表格/视频/图片/代码/更多）说的是文件长什么样，不回答「要不要留、要不要备份」 |
| 类型语义有重叠 | `harness/page.html` 判成「网页」，但它其实是测试夹具；`.json` 一律算「代码」，配置和数据混在一起 |
| 记忆混在文档里 | 17 个 `MEMORY.md` 现在和交付文档平级，占「文档」的 68% |
| 噪声无法排除 | 103 条过程文件必须靠类型硬猜，猜不出来 |
| 备份无从下手 | 「把产物传到云端」= 只能一条条手选 |

**所以：主维度应该换成「角色」，类型退居第二维。** 「分类」这个词也不要用——它和类型会混，叫**角色**。

---

## 2. 目标模型：三个正交维度

| 维度 | 回答的问题 | 取值 | 是否互斥 | 谁来决定 |
|---|---|---|---|---|
| **角色 role** | 这东西**要不要留、要不要备份** | 产物 / 过程 / 记忆 / 素材 /（未定） | 是（一条一个角色） | 规则给初值，**用户可改** |
| **类型 type** | 这是**什么格式** | 文档/表格/幻灯片/图片/矢量/视频/音频/代码/配置/网页/压缩包/其他 | 是 | 扩展名，全自动 |
| **会话 session** | 它**属于谁** | 会话目录 / `_shared` / `artifacts` | 是 | 路径，全自动 |

- 三者是**与关系**：`角色=产物 AND 类型=文档 AND 会话=xxx`
- 界面上只暴露「角色」和「类型」两排；会话做成**分组**（可选，P4）或保留现有来源筛选
- 默认视图 = **只看产物**。这一条是这次改版的核心：打开就是干净的。

---

## 3. 类型（type）重新规划

### 3.1 现状问题

| 现状 | 问题 |
|---|---|
| `code` 包含 `.json` | 配置/数据和源码混在一起；本工作区 61 个 code 里约 1/3 是 json |
| `web` 和 `code` 都吃 `.html` | `harness/page.html` 被归到 web，语义上它是测试夹具 |
| `image` 包含 `.svg` | svg 既可能是图标素材，也可能是被生成的矢量图 |
| 没有 `audio` | 语音/音频落到 other |
| 没有 `config` | `.yaml`/`.toml`/`.env` 落到 other |

### 3.2 新映射（12 类）

| 类型 | 扩展名 | 典型用途 |
|---|---|---|
| `doc` 文档 | md, mdx, txt, pdf, docx, rtf, epub | 说明、报告、设计稿 |
| `sheet` 表格 | csv, tsv, xlsx, xls, ods | 数据表 |
| `slides` 幻灯片 | pptx, ppt, key, odp | 演示 |
| `image` 图片 | png, jpg, jpeg, webp, gif, bmp, avif, ico | 位图 |
| `vector` 矢量 | svg | 图标 / 矢量图 |
| `video` 视频 | mp4, webm, mov, m4v, mkv | 录屏 |
| `audio` 音频 | mp3, wav, m4a, ogg, flac | 语音 / 音乐 |
| `code` 代码 | js, mjs, cjs, jsx, ts, tsx, py, ps1, sh, bat, sql, css, scss, go, rs, java, c, cpp, h | 可执行/源码 |
| `config` 配置 | json, yaml, yml, toml, ini, env, xml, conf | 配置、锁文件、数据快照 |
| `web` 网页 | html, htm | 可交互页面 |
| `archive` 压缩包 | zip, tar, gz, tgz, 7z, rar | 备份包 |
| `other` 其他 | 其余 | |

**和现在的差异**：`svg` 从 image 独立成 vector；新增 `config` / `audio`；`.json` 从 code 挪到 config；`web` 保持独立但只收 `.html/.htm`。

**注意**：类型**不进主 chip**。主 chip 只有角色；类型靠「卡片图标 + 颜色」快速区分，需要筛时点「更多」→ 类型多选，或直接搜 `type:code`。

### 3.3 图标与颜色

沿用现有 12 个 glyph，新增 `vector`（钢笔）、`audio`（音符）、`config`（齿轮）。颜色仍用 `--ap-hue` 6% 底色，不参与文字对比度。

## 4. 角色（role）设计

### 4.1 取值

| role | 含义 | 默认显示 | 参与备份 |
|---|---|---|---|
| `deliverable` 产物 | 用户要的交付物 | ✅ 默认视图 | ✅ |
| `scratch` 过程 | 测试脚本、截图、夹具、日志 | ❌ | ❌ |
| `memory` 记忆 | MEMORY/PERSONA/HANDOFF | ❌（单独入口） | 可选 |
| `asset` 素材 | 用户提供的输入（源图、参考、样例数据） | ❌ | ❌ |
| `unknown` 未定 | 规则拿不准 | ❌（进「待确认」队列） | ❌ |

### 4.2 自动规则（给初值，不是终审）

按优先级：

```
1. 手动标注（.artifacts.json）           ← 最高
2. memory : 名字匹配 ^(MEMORY|PERSONA|HANDOFF) 或路径含 memory/
3. scratch: 路径命中 screenshots|shots|harness|tests?|fixtures?|tmp|cache|node_modules
            或名字命中 ^(probe|diag|debug|check|test|verify|shoot|shot|closeup|narrow|arrange|fixture|grep|inspect)[-_.]
            或 *.log / package-lock.json
4. asset  : 路径命中 uploads|assets|input|素材（用户自己放的）
5. 其余    → deliverable
```

**实测**（本工作区）：memory 17 / scratch 103 / deliverable 22 —— 但产物里混进了 13 个 `verify-*.mjs`、`shoot-*.mjs`（规则没覆盖到 `verify/shoot`），说明**规则必然有漏判**。

### 4.3 为什么必须能手动改

同一份 `.mjs`，在 `harness/` 里是过程，在 `artifacts/` 里可能就是要交付的脚本。
同一张 `.png`，可能是截图，也可能是你花两小时画的设计稿。

所以设计成：**规则只负责「先摆好」，用户负责「最后确认」**。改动一次即永久生效（按 id 记录），规则再怎么升级也不覆盖用户的判断。

### 4.4 整理模式（P0 交互）

进入方式：顶部「整理」按钮，或首次升级时自动提示。

```
┌ 整理产物 ──────────────────────────────────────────────────┐
│ 142 个文件 · 自动判定：产物 22 · 过程 103 · 记忆 17        │
│ 已有 22 条人工确认                                    [×] │
├────────────────────────────────────────────────────────────┤
│ ▸ 2026-11-04-plugin-sidebar-entry (54)        [整个会话: 过程]│
│   ▸ screenshots/ (21)  全部标为 [过程▾]   ← 一键             │
│   ▸ harness/ (42)      全部标为 [过程▾]                     │
│   ▱ plugin-design-v2-category-autosync.md   [产物][过程][记忆]│
│   ▱ MEMORY.md                               [产物][过程][记忆]│
├────────────────────────────────────────────────────────────┤
│ 已选 0 · [全部设为产物] [全部设为过程] [重置为自动]  [完成]  │
└────────────────────────────────────────────────────────────┘
```

- 每条三态按钮：产物 / 过程 / 记忆（点一下切换，再点回到自动）
- 支持**按目录批量**：`screenshots/ (21) → 全部设为过程`
- 支持**按会话批量**：整个会话设为过程 / 产物
- 键盘：`J/K` 上下，`1/2/3` 设角色，`Space` 多选
- 完成后写 `.artifacts.json`，只记录**人工覆盖**，不复制整张表

### 4.5 「待确认」队列（P3，可选）

规则置信度低的（例如根目录下的 `.mjs`、无扩展名文件）单独进「待确认」角标，点进去就是整理模式筛好的子集。

## 5. 界面规划

### 5.1 默认视图（产物）

```
本地 22    云端 4    回收站 2                    [整理]  [⟳] [⚙]
全部 22 · 文档 9 · 代码 13 · 图片 0            [会话|共享] [最近修改 ▾] [▦]
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  plugin-design-v2 …│ │  artifact-management-plan │ │  README.md │
│  文档 · 12 KB      │ │  文档 · 8 KB              │ │  文档      │
└──────────────┘ └──────────────┘ └──────────────┘
```

- **默认只有产物**，顶部 tab 数字也按产物算（`本地 22`）
- 「全部 / 过程 / 记忆」放进一个「角色」下拉或第二排小 seg（默认收起）
- 类型变成**同一排里的次要 chip**（只显示当前结果里出现过的类型，带计数）—— 这就是你说的「另一个维度，方便快速区分」，但不占两条轴

### 5.2 角色切换

```
[产物 22] [全部 142] [过程 103] [记忆 17]      ← 一行 chips，默认停在“产物”
```
切到「全部」时，卡片带一个淡淡的角色角标（过程 = 灰色「过程」、记忆 = 「记忆」），一眼能看出为什么它在。

### 5.3 搜索语法（P3）

- `type:code` `role:scratch` `session:plugin-sidebar-entry` `size:>1mb`
- 普通输入仍然全文匹配文件名/路径

## 6. 数据与接口

### 6.1 存储

不改 `.index.json`（派生数据）。新增 `sessions/.artifacts.json`：

```json
{
  "version": 1,
  "roles": {
    "2026-11-04-plugin-sidebar-entry/harness/drive.mjs": { "role": "scratch", "at": "2026-11-06T01:40:00Z" }
  },
  "rules": { "scratchDirs": ["screenshots", "harness"], "scratchNames": ["probe", "diag"] },
  "updatedAt": "2026-11-06T01:40:00Z"
}
```

- 只存**人工覆盖**；规则是代码里的默认值，允许用户在设置里改目录/前缀名单（P3）
- 文件被重命名/移动后 id 变化 → 标记失效，回到自动判定（可接受；或按 `size+mtime` 迁移，P4）

### 6.2 接口

| 接口 | 变化 |
|---|---|
| `POST /items` | 新增 `role`（产物/过程/记忆/全部，默认 `deliverable`）、`type`；返回 `role`、`roleSource: 'auto'｜'manual'`；`facets.role` / `facets.type` |
| `POST /artifacts/roles` | 批量设置 `{ ids: [...], role }` 或 `{ ids: [], role: null }`（重置为自动） |
| `POST /status` | 返回 `counts: { deliverable, scratch, memory, asset, unknown }` |

### 6.3 兼容

- 老版本客户端只看 `kind`，新字段是增量，不影响
- `role` 默认 `deliverable` 会让老客户端看到"变少了"——所以**升级后第一次打开**弹一次说明（见 §7）

## 8. 备份与自动同步（角色决定范围）

这一版把「分类」和「备份」真正连起来：

| 范围 | 谁会被传 |
|---|---|
| **只产物（默认）** | `role === 'deliverable'` |
| 产物 + 记忆 | 加上 `memory`（`MEMORY.md` 跨机迁移有用） |
| 手动选择 | 现在这套，选谁传谁 |

- **过程 / 素材永不上传**（省流量、避免把测试垃圾传上去）
- 自动同步（定时）的范围 = 上面选的那一档，**且只处理已有云端记录的条目**；「新产物自动上传」作为独立开关，默认关
- 云端 tab 顶部显示：`自动备份：产物（22 个）· 每 15 分钟 · 上次 01:10 传了 2 个`

## 9. 分期

| 期 | 内容 | 估时 | 价值 |
|---|---|---|---|
| **P1** | 角色（规则 + 手动标注）+ 默认只看产物 + 角色 chips + 计数 | 1 天 | 打开就干净，解决 80% 噪声 |
| **P2** | 类型重划（12 类）+ 图标 + 类型 chip | 0.5 天 | 快速区分 |
| **P3** | 整理模式（按目录/会话批量、键盘、待确认队列） | 1 天 | 一次整理长期受益 |
| **P4** | 额外产物根（把 `dsh-plugin-artifacts` 这类项目目录纳入）+ 备份范围 + 自动同步 | 1.5 天 | 真正能备份交付物 |

P1 单独上就有明显收益，P2 可并入 P1。

## 10. 明确不做的事

| 不做 | 原因 |
|---|---|
| 读会话 transcript 判断"谁生成的" | `session.v4.jsonl.zstd` 是多帧 zstd，Node 只能解出第一帧；格式还可能变 |
| 用内容哈希判断"是否上传过" | 实测 377 个 blob 只命中 3 个，且分不清"用户传的"和"我读过的" |
| 自动移动/删除文件 | 整理只改标记，不动磁盘 |
| AI 判断"这个文件重不重要" | 不可解释，且每次结果可能不同 |
